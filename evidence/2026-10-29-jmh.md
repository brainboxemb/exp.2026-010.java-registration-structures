This run contains the final functional desktop shape used for the architecture decision:

- compact production StageTiming semantics;
- allocation-free compact elapsed parsing in the state hot path;
- RaceData-owned current stage starts;
- `onlyRetainedRow` fast path for normal start/sync operations;
- `onlyValidRow` fast path for normal REV;
- exceptional list scans only when multiple retained/valid rows exist.

Later branch changes around this result are documentation/workflow-only unless a newer evidence
run is explicitly cited.

## Candidate-only cross-check on a second runner allocation

A second forked run used the same functional structures but restricted JMH to the two viable
candidates:

https://github.com/brainboxemb/exp.2026-010.java-registration-structures/actions/runs/40858497640

| Operation | Sorted array | Pooled AVL |
| --- | ---: | ---: |
| rank lookup | 16.928 ns | **9.705 ns** |
| ranking replace/prepare/rank/restore | **118.074 ns** | 171.558 ns |
| direct row sync | 13.596 ns | **11.802 ns** |
| sync one id, one retained row | 18.084 ns | 17.443 ns |
| sync one id, multiple retained rows | **418.469 ns** | 423.310 ns |
| 500-row snapshot | 6.214 µs | 6.120 µs |
| start change + sync, one retained row | **182.205 ns** | 245.477 ns |
| start change + sync, multiple retained rows | **2.205 µs** | 2.370 µs |

Again, both candidates were effectively allocation-free.

The absolute numbers moved because this is a shared CI runner, but the useful conclusions are
more trustworthy after comparing two independent forked runs:

**Stable across both runs**
- AVL wins pure rank lookup.
- SortedArray wins the ranking mutation roundtrip.
- SortedArray wins the normal single-row start-change + sync path.
- one-id sync paths are close enough that the surrounding list/index dominates.

**Not stable enough to drive architecture**
- the small full-snapshot difference;
- the small exceptional multiple-row start-change difference.

In the first run AVL was ~0.56 µs faster for the 500-row snapshot and ~60 ns faster for the
exceptional start path. In the second run the snapshot gap shrank to ~0.09 µs and SortedArray
won the exceptional start path.

That variability is exactly why those small differences should not justify the extra AVL
implementation/memory complexity.

## Decision

The final desktop evidence strengthens the choice of **SortedArrayRanking**.

Pooled AVL advantages:
- ~3 ns faster pure rank lookup;
- ~0.56 µs faster complete 500-row snapshot;
- ~60 ns faster exceptional two-row start-change roundtrip.

SortedArray advantages:
- ~21% faster ranking mutation roundtrip;
- ~9% faster normal single-row start-change + sync;
- effectively identical single/multiple registration sync outside rank-heavy reads;
- ~22 KiB smaller complete retained graph;
- much simpler implementation;
- no tree balancing, subtree bookkeeping or node pool.

For a normal design population around 500, the AVL advantage is concentrated in repeated rank
reads. The sorted array wins or ties the state-changing paths and is materially simpler/smaller.

Therefore:

> **SortedArrayRanking remains the preferred production candidate unless the physical Pi Zero
> qualification shows a material reversal.**

Rebuild+sort and TreeMap remain evidence/reference implementations only.

## Remaining hardware gate

The next performance decision should come from the physical ARMv6 target, not from inventing
more desktop data structures.

Use the self-contained bundle described in `PI.md` to compare SortedArray and pooled AVL on:

- mutation roundtrip;
- single/multiple registration sync;
- snapshot;

If the Pi does not show a material reason to pay the AVL complexity/memory cost, the ranking
experiment is complete.
