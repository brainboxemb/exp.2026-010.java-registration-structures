## RankingIndex in isolation

### Pure current-rank lookup

| RankingIndex | Mean | Error | Allocated |
| --- | ---: | ---: | ---: |
| Rebuild + sort, already prepared | 9.955 ns | ±0.088 ns | ~0 B/op |
| Sorted primitive array | 12.031 ns | ±0.387 ns | ~0 B/op |
| TreeMap | 528.067 ns | ±9.334 ns | 127.818 B/op |
| Pooled AVL | **8.281 ns** | ±0.293 ns | ~0 B/op |

The pooled AVL is fastest for a pure lookup, but the sorted primitive array is still only
about 12 ns at the normal ~500-entry size.

TreeMap is both much slower and allocates because its standard implementation has no subtree
occurrence counts; `rankOf()` walks a `headMap` and boxed entries.

### Replace + prepare + rank + restore roundtrip

Each invocation removes one value, inserts a temporary value, prepares/reads its rank, then
removes that temporary value and restores the original value.

| RankingIndex | Mean | Error | Allocated |
| --- | ---: | ---: | ---: |
| Rebuild + sort | 16,669.739 ns | ±572.601 ns | 1,027.806 B/op |
| Sorted primitive array | **97.012 ns** | ±1.614 ns | ~0 B/op |
| TreeMap | 1,886.158 ns | ±21.519 ns | 487.461 B/op |
| Pooled AVL | 143.250 ns | ±2.485 ns | ~0 B/op |

At ~500 entries the sorted primitive array wins this mutation-heavy operation by about 32%
over the pooled AVL despite its O(N) shifts. The small contiguous array is cheap enough that
the theoretically better tree complexity does not pay for its pointer/tree maintenance here.

## 500-row snapshot

A snapshot visits all 500 retained rows and asks for current rank for every valid/rankable row.

| RankingIndex | Mean / snapshot | Error | Allocated |
| --- | ---: | ---: | ---: |
| Rebuild + sort | 6.286 µs | ±0.075 µs | ~0 B/op |
| Sorted primitive array | 5.867 µs | ±0.295 µs | ~0 B/op |
| TreeMap | 424.046 µs | ±26.521 µs | 64,008 B/op |
| Pooled AVL | **5.371 µs** | ±0.070 µs | ~0 B/op |

The pooled AVL is about 0.50 µs faster than the sorted array for the complete 500-row
snapshot, roughly a 9% difference. In absolute terms both are only a few microseconds on this
desktop runner.

TreeMap is unsuitable for this read pattern: every rank query traverses the map and allocates,
which compounds across 500 rows.

## Start change + affected-registration synchronization

Each JMH invocation:
1. changes one registrationId start time;
2. updates RankingIndex through RegistrationList;
3. visits the affected registration;
4. restores the original start;
5. visits the restored registration.

| RankingIndex | Mean | Error | Allocated |
| --- | ---: | ---: | ---: |
| Rebuild + sort | 12.329 µs | ±0.209 µs | ~0 B/op |
| Sorted primitive array | 1.684 µs | ±0.026 µs | ~0 B/op |
| TreeMap | 4.840 µs | ±0.427 µs | 514.762 B/op |
| Pooled AVL | **1.666 µs** | ±0.023 µs | ~0 B/op |

Sorted array and pooled AVL are effectively tied for this complete operation. Their error
ranges overlap.

## Interpretation

At the normal ~500-entry design point:

### Rebuild + sort

It remains useful as a baseline but is not attractive for live mutations. Re-sorting after a
change dominates the cost.

### TreeMap

It is convenient code but is a poor fit:
- rank lookup is hundreds of ns rather than ~10 ns;
- a 500-row snapshot takes hundreds of microseconds rather than ~5–6 microseconds;
- rank reads and mutations allocate substantially.

It should stay only as a standard-library comparison.

### Pooled AVL

It provides the best pure rank-read performance and the fastest snapshot in this desktop JMH
run. Its advantages over SortedArray are:
- ~3.8 ns faster pure rank query;
- ~0.5 µs faster complete 500-row snapshot.

Its disadvantages are:
- considerably more complex implementation;
- hundreds of Node objects/pool references;
- slower mutation roundtrip: 143 ns versus 97 ns for SortedArray;
- essentially no measurable advantage on start-change + sync.

### Sorted primitive array

It has the best balance at the current design point:
- ~12 ns rank lookup;
- fastest mutation roundtrip;
- ~5.9 µs complete 500-row snapshot;
- effectively tied with AVL on start-change + sync;
- no normal steady-state allocation;
- one compact primitive array and simple binary-search/arraycopy implementation.

## Current candidate

**SortedArrayRanking is now the preferred RankingIndex candidate for the ~500-registration
production design.**

PooledAvlRanking remains valuable as:
- a scaling reference;
- a fallback if Pi Zero results show rank/snapshot reads dominate unexpectedly;
- evidence that O(log N) is available without steady-state allocation.

Before removing the AVL comparison or changing production:
1. measure retained object-graph size;
2. run the same selected JMH scenarios on the Pi Zero;
3. validate production StageTiming semantics.

The simpler candidate should win unless the remaining measurements show a material reason to
pay the AVL complexity cost.
