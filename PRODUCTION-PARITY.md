# Production parity

Reference production repository:

`brainboxemb/2026-010-02.java.timing-point-application`

Reference commit inspected:

`0bda66147c5a096b560c9bff546211a947936938`

This document records which production semantics Experiment 010 now matches and which
responsibilities deliberately remain outside `RegistrationList`.

## 1. RegistrationList input boundary

Production `ActiveRegistrations.apply(...)` accepts a committed TimingRecord but changes
registration state only when:

```text
kind == AUTOMATIC_REGISTRATION or MANUAL_REGISTRATION
and
record.locationId == currently open LocationId
```

Experiment 010 deliberately keeps this filter **outside** `RegistrationList`.

The intended integration boundary is:

```text
LogBook / DataTask
    |
    | filter registration kind + active LocationId
    v
RegistrationList.add / revoke
```

RegistrationList therefore does not need to retain LocationId or TimingRecord kind per row.

## 2. OPEN rebuild semantics

Production DataTask:

1. starts at LogBook sequence 1;
2. reads bounded batches of 64 records;
3. requires strictly contiguous sequence numbers;
4. replays the complete LogBook through the active LocationId filter;
5. resolves the **current RaceData stage start** for every registration ADD;
6. keeps historical team/registration projection changes silent;
7. calculates final ranking once after catch-up;
8. only then allows active projection reads.

An OPEN does **not** mean "only records since the most recent OPEN record".

If LocationId 1 was opened, closed, another WP used, then LocationId 1 is opened again,
all relevant LocationId-1 registration history in the LogBook is reconstructed.

Experiment 010 matches the derived-state part with:

```java
list.beginInitialLoad();
// replay filtered ADD/REV records using current starts
list.finishInitialLoad();
```

No display mutation revisions are generated by that replay. The first snapshot has marker 0.

The asynchronous 64-record LogBook paging remains a DataTask/LogBook responsibility and does
not belong inside RegistrationList.

## 3. ADD semantics

For one relevant ADD, production retains:

- original committed LogBook sequence;
- absolute effective/passage time as epoch milliseconds;
- packed RegistrationId;
- the RegistrationId's current compact UTC stage start, when known;
- valid=true.

Experiment 010 retains the same scalar information in primitive arrays and additionally caches
the derived elapsed milliseconds.

Caching elapsed is safe because it is recalculated whenever that RegistrationId's stage start
changes.

## 4. REV semantics

Production REV invalidates the **newest still-valid ADD** matching:

```text
registrationId
+
effective/passage time
```

The retained ADD row stays in its original chronological position.

An unmatched REV does not change registration state.

Experiment 010 matches this rule, with an optimization:

- `validCount == 1`: inspect `onlyValidRow` directly;
- `validCount > 1`: scan the retained rows backwards.

The optimization does not change matching semantics.

## 5. Compact UTC stage-start semantics

Production does not represent every stage start as epoch milliseconds.

Compact UTC values are:

```text
HHmmsscc            time only, no date
yyyyMMddHHmmsscc    explicit UTC date/time
```

Experiment 010 now uses the same representation in `RegistrationList.startTimes[]`.

`passageTimes[]` remains absolute UTC epoch milliseconds.

`StageTiming` in this experiment mirrors the production rules:

### Dated start

```text
elapsed = passageEpochMillis - explicitStartEpochMillis
```

A negative elapsed is unresolved.

### Time-only start

The date is deliberately **not invented**.

The start is treated as the same UTC day or previous UTC day relative to the passage.
The derived elapsed is accepted only when:

```text
elapsed < 12 hours
```

Exactly 12 hours and longer is unresolved.

This allows deterministic midnight rollover while rejecting an ambiguous missing date.

### Local input normalization

For protocol-local input:

- absolute timestamps retain their instant;
- local date/time is converted using the source zone;
- DST gaps and overlaps are rejected;
- time-only input uses the zone offset at one message reference instant;
- a variable-offset zone is rejected when a transition lies within ±12 hours of that
  reference.

Parity tests cover midnight, the 12-hour boundary, explicit date/year rollover and Amsterdam
DST gap/overlap behavior.

## 6. Stage-start message batching

Production IF-06 currently allows at most:

```text
MAX_STAGE_START_CHANGES = 16
```

One complete STAGE_STARTS message is validated first, then its scalar SET/DEL changes are
applied, and production advances `stageStartRevision` once for the complete changed message.

The old whole-list ranking implementation also recalculates ranking only once after the
message.

Experiment 010 does not need a special bulk-ranking API:

- each SET/DEL updates the affected cached row(s) and RankingIndex incrementally;
- no `RankingIndex.prepare()` is forced by the mutation itself;
- a rebuild+sort candidate therefore still sorts only when a read requires prepared rank state;
- each changed RegistrationId may emit one compact START_CHANGED mutation.

Because one protocol message carries at most 16 stage-start changes, per-id mutation entries
are bounded and do not justify another bulk-mutation protocol.

## 7. Display synchronization difference

Current production/test-client synchronization does not yet have the Experiment 010 mutation
ring.

Today it uses projection metadata:

- count;
- lastMutationSequence;
- lastRevokeSequence;
- stageStartRevision.

ADD-only growth may be appended by sequence. A REV, stageStartRevision change, location change
or ambiguous mutation forces a bounded **full registration reread**.

Experiment 010 is intended to replace that expensive invalidation pattern with:

```text
snapshot + mutationRevision
then
visitMutationsAfter(revision)
```

Row ADD/REV mutations point at stable row indices.
START_CHANGED points at RegistrationId.

If a mutation has `RANKING_CHANGED`, the display refreshes current rank for rows it is
actually presenting rather than synchronizing every row whose derived numeric rank may have
changed.

## 8. Unique registration/team count

Production currently has a separate `RegisteredTeams` projection because TeamId resolution can
come from fixed EventData or live RegistrationId-to-TeamId assignments.

Experiment 010's `RegistrationIndex` gives:

- unique retained RegistrationId count;
- unique currently valid RegistrationId count.

Those are **registration counts**, not automatically the final unique TeamId count.

A production refactor must preserve the TeamId resolution rule instead of assuming one
RegistrationId always equals one team.

## 9. Remaining production integration work

The data-structure experiment now matches the important registration/timing semantics, but it
still intentionally does not own:

- LogBook persistence/range reads;
- LocationId and TimingRecord-kind filtering;
- Task Lane/caughtUp lifecycle;
- TeamId assignment projection;
- HTTP/API wire format;
- the engineering client's final snapshot/mutation consumer.

Those should be adapted around RegistrationList rather than moved into it.

## 10. Production migration contract

Before replacing production ActiveRegistrations, regression fixtures should prove:

1. same-location history across multiple OPEN/CLOSE periods reconstructs identically;
2. other LocationIds and non-registration records are ignored;
3. automatic and manual registrations are both retained;
4. REV chooses the newest matching still-valid ADD;
5. unmatched REV is a no-op for registration state;
6. current RaceData stage start is used when reconstructing historical ADD rows;
7. compact time-only starts preserve midnight/<12-hour behavior;
8. stage-start messages of up to 16 changes converge correctly;
9. snapshot + mutations converges to the same rows/ranks as a full production reread;
10. RegistrationId-to-TeamId resolution remains correct.
